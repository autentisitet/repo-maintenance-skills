# Community Documents

## Issue Templates

If a template is long or appears to make every field mandatory, state that it is guidance:

> This is a suggested template, not a mandatory reporting format. Use the
> sections that help communicate the problem; a clear free-form request is welcome.

Use fields that request actionable information rather than empty headings such as “Describe the issue.”

---

## Contributing Guide

- Use a respectful, welcoming tone without teaching basic Git unless the repository requires it.
- Organize environment setup, development, checks, commits, and issue reporting around the actual workflow.
- Give commands that exist in the repository and explain required pre-submit checks and failure diagnosis.

---

## Security Policy

State the supported versions, for example:

```text
Security fixes are targeted at the latest version on the default branch. Older
releases may not receive fixes.
```

Provide a private reporting channel such as email or GitHub Security Advisories. Do not ask reporters to disclose vulnerabilities in public issues.

---

## Disclaimer and License Material

- Ask qualified counsel to review text intended to have legal effect. When maintaining translations, identify the controlling version and keep them synchronized.
- Prefer clear modern English while preserving precise established legal terms where ordinary wording would lose meaning.
- Define scope across software, data, model output, and other distributed material without turning a repository notice into an exhaustive legal treatise.
- Follow upstream licenses when modifying or redistributing code, and document source and modification scope.
- Verify every third-party asset license, including fonts, icons, weights, and datasets.
- Before relicensing, verify the current license, contributor agreements, and every contributor's authority.
